# GCP selection protocol (fixed 2026-10-19, before any method's positional errors were computed)

## Sources
- **True coordinates:** OSM vector geometry (Overpass snapshot in `data/raw/manifest.json`), converted to
  EPSG:32643 metres. For crossings this is the exact intersection of the two OSM ways (`gcp/candidates.csv`,
  generated by `python -m mapalign.gcp candidates`). OSM's own positional accuracy is unknown, plausibly
  5–20 m, and is a limitation.
- **Historical pixel:** the same feature on the 1926 scan (full-resolution pixels, OpenCV centre
  convention), picked by visual inspection.
- **Crop centring:** picking crops are centred using the *printed-corner prior only*, never with SIFT,
  LoFTR or manual-fit transforms.

## Who picked the points
The points in `fitting_points.csv` were picked by **Claude (AI assistant)** from zoomed image crops, at the
user's request. **They have not yet been verified by a human.** `thumbnails_*.jpg` shows each pick for review.
Method C is therefore "AI-picked, human-reviewed GCPs" (review logged below). Manual interaction
time is not reported as human effort.

## Feature priority (most to least reliable for 1926 → today)
1. Railway–road crossings and railway–river crossings (alignments of the 1920s metre-gauge lines largely persist).
2. Road bridges over the Cauvery and its branches; old canals that appear on the 1926 sheet.
   The Vishveshvarayya canal postdates 1926 and is **not eligible**.
3. Junctions of old main roads that appear on both maps with the same geometry.
4. Railway stations: the OSM node position is ambiguous, so these are used only if nothing else exists in a cell.

A candidate is rejected (before any fitting) if the feature is not visible on the 1926 map, if its local
geometry clearly differs (realignment), or if the intersection cannot be located to roughly ±5 px (±27 m).

## Spatial design
The neatline area is divided into a 5×5 grid (`r{row}c{col}`, r0 = north, c0 = west).
- **Fitting set (Method C), 13 points:** one point in each of cells r0c0, r0c2, r0c4, r1c1, r1c3, r2c0,
  r2c2, r2c4, r3c1, r3c3, r4c0, r4c2, r4c4. This gives corners, edge midpoints, centre and a diagonal lattice.
- **Evaluation set (Phase 6), 20 points:** spread over all 25 cells, using features not used for fitting,
  at least 1 km from every fitting point. They are picked under this same protocol and never used for any
  fitting, threshold or model choice.
- If a cell has no acceptable feature, the nearest acceptable feature in an adjacent cell may be used instead;
  the substitution is recorded in `notes`. If none exists, the cell is left empty and the gap is reported.
  Points are never invented. *(Amendment of 2026-10-19, made during fitting-point picking and before any
  positional error had been computed. The reason was that the western cells have almost no features that survive from 1926.)*

## Model for Method C
Projective homography, historical px → reference px, least squares over all fitting points (no RANSAC). It
is the same transform family as Methods A/B. Leave-one-out residuals are reported as a fitting diagnostic,
which is **not** the evaluation error.

## Evaluation-set log (2026-10-19, written before any method was evaluated at these points)
- Picked by Claude (AI) from crops centred with the printed-corner prior. No method overlay, transform or
  prediction was viewed while picking.
- **12 points, not 20.** Every candidate in the 5×5 grid was reviewed (`gcp/candidates.csv`, picking sheets in
  `gcp/picking/`, not committed). The rest were rejected for these reasons:
  - post-1926 features: Varuna/Vishveshvarayya canal network, ring roads, NH link roads;
  - realignment: the Mysore–Nanjangud line inside the city lies about 280 m from its 1926 course (gauge conversion);
  - ambiguity: road junctions whose 1926 geometry does not clearly match.
- **Coverage.** No evaluation point lies in row r4 (the southern fifth of the sheet) or in the Mysore city cells
  r3c1–r3c3. The southern results therefore rest on extrapolation, and this is reported as a limitation.
- **Pre-evaluation QC.** This is the same graticule-offset rule as for the fitting set (>3 robust σ), and it uses no
  method output. Two picks failed it and were re-examined:
  - E12: the wrong road had been picked, so it was re-picked;
  - E06: the position had been extrapolated, so it was re-read at 6× zoom.
  No point was dropped. After the corrections, all 12 points have |z| ≤ 3 (max 2.99).
- **Lock.** SHA-256 of `evaluation_points.csv` is recorded in `data/raw/manifest.json` (`evaluation_points_lock`).
  `mapalign.evaluate` refuses to run if the file changes.

## Independent re-pick (procedure fixed 2026-10-22, before any re-pick)
- **Kits:** `gcp/repick_kit_fitting/` (9), `gcp/repick_kit_evaluation/` (12) and `gcp/repick_kit_extra/` (57 new
  candidates in the 15 cells with no evaluation point, each ≥ 1 km from every existing point). Crops are centred with
  the printed-corner prior only; no existing pick appears in any kit.
- **Picking:** with `python -m mapalign.picktool <template> --picker "<name>"`, which records full-resolution pixel
  coordinates and the seconds per point. The picker does not open `gcp/*_points.csv`, `results/` or the report site
  until all three kits are done. A feature that cannot be identified on the 1926 sheet is skipped, never guessed.
- **Scoring:** `python -m mapalign.robustness picker --fitting … --repick …` and `… extra_points --points …`. Method C
  is refitted on the human fitting picks with the same QC rule (> 3 robust σ). The frozen transforms of the automatic
  methods are not changed.
- **Reporting:** the original (AI-proposed, human-reviewed) results stay as published and locked; the human re-pick is
  reported next to them as a separate run, with the picker-to-picker distances and the total human time. The filled
  templates are committed unchanged and their SHA-256 recorded in the output JSON.
